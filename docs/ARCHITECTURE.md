# Technical architecture

Status: **implemented on `development`; production release owner-gated.**

## Topology
- Repo: `debro-finance/debro-web`, institutional website only.
- Canonical origin when approved: `https://debro.finance`; `www` redirects to apex. `app.debro.finance` belongs to the separate application repository.
- Next.js App Router, strict TypeScript, Tailwind CSS 4, Vercel.
- Vercel GitHub integration, Neon and Vercel Analytics are owner-configured; this repository reuses them and provisions no duplicates.
- Production branch: `main`. `development` and feature PRs produce preview deployments.

## Rendering and routes
- `/` is a static-rendered server component page. Interactive islands are limited to the mobile menu and waitlist form.
- `POST /api/waitlist` is a Node.js Route Handler (`force-dynamic`, `no-store`).
- `robots.txt`, `sitemap.xml`, `/icon.svg` and `/apple-icon.png` are generated by Next.js metadata routes/file conventions.
- 404 responses use a branded `not-found.tsx`.

## Waitlist data flow
1. Client submits JSON: `email`, `consent`, hidden `company` honeypot. Optional UTM attribution fields are parsed only when `WAITLIST_ATTRIBUTION_ENABLED=true`; otherwise they are ignored and never stored.
2. Route enforces a 4 KB body limit and derives a hashed client key from `x-forwarded-for`/`x-real-ip`.
3. `src/server/waitlist.ts` validates, checks the honeypot, applies the in-memory limiter, and calls a narrow database interface.
4. `src/server/db.ts` uses `@neondatabase/serverless` over HTTP with a parameterized conflict-safe insert into `public.waitlist_subscribers`; zero-row inserts require a follow-up check confirming the duplicate exists. When approved attribution is present, the insert uses the additive attribution columns but still preserves original attribution on conflict.
5. Successful inserts, verified duplicates and honeypot submissions return the same generic response. Database failures return safe codes without SQL, stack traces or PII.

The service depends on a `WaitlistDb` interface, so unit tests and PostgreSQL integration tests exercise the same behavior without importing the Neon adapter.

## Configuration gates
| Variable | Behavior |
| --- | --- |
| `NEXT_PUBLIC_SITE_URL` | Canonical origin; trailing slash trimmed |
| `SITE_INDEXABLE` | Must be `true` **and** `VERCEL_ENV=production` for indexing |
| `WAITLIST_ENABLED` | Explicit `true` required on Vercel; local development enables with a database URL |
| `WAITLIST_ATTRIBUTION_ENABLED` | Optional UTM attribution collection; default off, owner approval required before enabling |
| `DATABASE_URL` | Server-only Neon/PostgreSQL connection string |
| `RATE_LIMIT_SALT` | Optional salt for in-memory rate-limit hashes |

The form's enabled/disabled presentation is rendered at build time. Changing `WAITLIST_ENABLED` in Vercel requires a redeploy; the API checks the variable at request time, so disabling it always blocks writes.

## Security and privacy baseline
- Server-side Zod validation and conservative lowercasing before persistence.
- Parameterized SQL, unique normalized email constraint and database check constraints.
- 4 KB request limit, honeypot and 5 requests / 10 minutes per hashed visitor key.
- The rate limiter is in-memory per serverless instance and is an abuse deterrent, not a distributed guarantee. Only a SHA-256 hash of the salted IP is retained in memory, never written to storage or logs.
- No database errors, SQL, connection strings, emails or IPs are returned to visitors or logged.
- Security headers: `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`; `X-Robots-Tag: noindex, nofollow` on non-approved deployments.
- No wallet, trading, finance or admin functionality exists in this repository.
- Emails are used only for a launch-availability announcement with explicit consent.

## SEO behavior
- Rich metadata, canonical URL, Open Graph/Twitter cards, JSON-LD `Organization` + `WebSite` with substantiated facts only.
- Non-production and non-approved deployments are `noindex` in both metadata and response headers.
- `robots.txt` disallows all crawling and `sitemap.xml` is empty until indexing is approved. Once approved on Production, robots allows `/`, publishes the sitemap URL and lists the canonical page.

## Vercel deployment behavior
- Automatic Git-triggered deployments are enabled only for `main` (Production) and `development` (Preview), configured via root-level `vercel.json` using `git.deploymentEnabled` (`"**": false`, `"main": true`, `"development": true`).
- Feature branches (`feature/*`, `chore/*`, `fix/*`) do not receive automatic Vercel deployments; PRs still run GitHub Actions CI and auto-merge into `development`.
- This does not change branch protections, the existing Vercel project, or manual deployment capability.
- Vercel preview deployments may still be created manually via the Vercel CLI/dashboard if needed.

## Deferred until go-live
Domain/DNS/TLS, approved legal disclosures and contact route, production indexing, public collection, announcement email provider, and any paid service or plan change. All remain owner-controlled.
